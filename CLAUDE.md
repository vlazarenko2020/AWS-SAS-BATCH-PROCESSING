# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is **not** an application codebase — it's the operational deployment tree for a single cron-driven job, `S3_Bucket_processing`, that watches an S3 bucket for `.FLAG` files, runs a matching SAS program when one appears, e-mails the result, and backs up the output. It runs on a SAS/Linux server (`sas-server.example.com`) under two Linux service accounts, `EMSERVICEUSER` and `MRSERVICEUSER`.

This tree was split out of a larger multi-job operational repo (which also had filesystem-flag-based jobs) to isolate the S3-based processing into its own project. There is no CI and nothing to "lint". Python deps (`boto3`) are declared in `pyproject.toml` and pinned in `uv.lock` (both committed), managed with `uv` (`uv sync` creates/updates `.venv`) — but that's the extent of "build" here. Validating a change means tracing the flow below and, where possible, running the `.sh` wrapper with the `test` argument (output goes to console instead of a log file).

`tests/` holds standalone, framework-free verification scripts (no pytest/unittest runner - each is directly executable and prints `PASS`/`FAIL` per case, exiting non-zero on failure): `python3 tests/test_ClassS3FlagFile_auth.py` covers `ClassS3FlagFile`'s bucket/folder/file_mask authorization matching and `$VAR` env-var resolution using fake fixtures (no real AWS calls); `bash tests/test_DEPLOYMENT.sh` covers `DEPLOYMENT.sh`'s fresh-create and decline-overwrite paths against an isolated temp copy with fake credentials, running it with `DEPLOYMENT_SKIP_S3_CHECK=1` so it never installs packages or calls AWS. Both are safe to run anywhere - they never touch the real `S3_Bucket_processing/info/s3_folder_mask_aws-key.info`/`AWS_KEY/.env-*` files or real AWS/S3.

`DEPLOYMENT.sh` (repo root) is the one-time setup script a deployer runs after cloning to a new server, per `S3_Bucket_processing/__NOTES_Deployment_script.txt`: it runs `uv sync` (against the repo's `pyproject.toml`/`uv.lock`) to create `.venv` and install pinned deps (`boto3`), detects whether a real `sas` executable is available on the machine (`command -v sas` on `PATH`, plus the two known real install paths documented in `COMMON/z_config.py`) and rewrites `z_config.py`'s `sas_bin` line accordingly — real path if found, `../FAKE-SAS-BIN.sh` if not — checks that the repo-root `sas01_sasdata_PROD_S3_Bucket_processing` symlink exists and resolves to a real directory (prompting the deployer for the real target path and `ln -s`-ing it if missing/broken), then prompts for the real AWS access key id/secret for each `$VAR`-referenced combination in `S3_Bucket_processing/info/s3_folder_mask_aws-key.info` and writes them to `AWS_KEY/.env-EMSERVICEUSER`, then uses that same `.venv`'s `boto3` to actually verify access (`head_bucket` + `list_objects_v2`) to every bucket/folder listed there, failing loudly per-combination if access doesn't work. Setting `DEPLOYMENT_SKIP_S3_CHECK=1` skips the `uv sync`/live-verification steps and the symlink check (credential collection and the SAS-executable detection still run) - this is what makes the script safe for `tests/test_DEPLOYMENT.sh` to exercise (that test's isolated temp copy has no `COMMON/z_config.py`, so the SAS-detection step just logs a warning and skips, and the symlink check is skipped outright so it never needs an interactive prompt). `S3_Bucket_processing/__NOTES_about_S3.txt` documents the real target S3 account/bucket/region/folder layout that `s3_folder_mask_aws-key.info` and the wrapper `.sh` must agree on.

## Repository layout

- `COMMON/` — shared Python library.
  - `z_config.py` is the **only file ever imported** (`import z_config`) and therefore the single source of active configuration. Per-job settings live in one list, `l_prog_config`: each entry is a single-key dict `{path_name: {settings}}`, where `path_name` is the same job/system-name string used throughout this tree (e.g. `'S3_Bucket_processing'`, matching the `-s`/`SYSTEM-SHORT-NAME` value) and `{settings}` holds `path_to_user`, `path_to_mailfile`, `path_to_systemname`, `path_to_logfile`, `path_to_sasfile`, `compress`, `path_to_ftp`, `path_to_aws_key`, `mail`. `mail` is itself a dict — `{'SMTP': ..., 'from': ..., 'to': [...]}` — holding that job's e-mail delivery config: `SMTP` is either a real SMTP server address (e.g. `'smtp.example.internal'`, for `ClassMailSend.mail_send_ONE_attach`) or the literal sentinel string `'SES'` (for `ClassMailSend.mail_send_ONE_attach_SES` instead — see `ClassSASProgram.f_send_email_or_post_to_webhook`); `from`/`to` are the actual FROM address and TO recipient list used for that job's status e-mails (CC is always forced to `[]`). Look up a job's settings with `z_config.f_get_prog_config(path_name)`, which returns the settings dict or `None` if no entry matches — call sites do `z_config.f_get_prog_config('S3_Bucket_processing')['path_to_sasfile']` etc. rather than indexing a dict per field. (This replaced eight separate parallel dictionaries — `dic_path_to_user`, `dic_path_to_mailfile`, `dic_path_to_systemname`, `dic_path_to_logfile`, `dic_path_to_sasfile`, `dic_compress`, `dic_path_to_ftp`, `dic_path_to_aws_key` — each of which needed a new entry per job/path, all keyed by the same string; if you see stale references to any of these in comments or notes elsewhere in the tree, they describe the old structure. The `mail` sub-dict similarly replaced four standalone globals — `c_smtpserver`, `c_ses_verified_from_addr`, `c_ses_verified_to_addr_list`, `c_to_addr_list_to_add_to_recipient_list` — that used to hold this same information outside `l_prog_config`.) There is no separate PROD/DEV config file in this tree; if you need to snapshot an alternate config, keep the naming convention `z_config_PROD.py`/`z_config_DEV.py` used in the parent repo (copy-over-`z_config.py`, no env-var switch), but none currently exists here.
  - `Modules/` — logic as free functions (`f_*.py`) and a few classes (`Class*.py`). Every file here is imported by the entrypoint chain.
  - `sas_ftp_and_S3_Bucket_processing.py` is the entrypoint script, invoked with `-t S3 -s S3_Bucket_processing -b <bucket>/<prefix> -d S3_Bucket_processing -n <thread> -m <file_mask>`. `-d` here is a "fake" filesystem path only used as a `z_config` dictionary key, not a real directory.
  - `Modules/m_mail_send_ONE_attach.py` — defines class `ClassMailSend` with two static methods sharing a `_build_message` helper (HTML `MIMEMultipart`, attaches the file at `f_file_to_attach_with_path` if given): `mail_send_ONE_attach(f_from_addr, f_to_addr_list, f_cc_addr_list, f_subject, f_telo, f_file_to_attach_with_path, f_smtpserver)` sends via `smtplib.SMTP(f_smtpserver)` with no auth (the SMTP server address is passed in by the caller — see the `mail` sub-dict in the `z_config.py` bullet above); `mail_send_ONE_attach_SES(f_from_addr, f_to_addr_list, f_cc_addr_list, f_subject, f_telo, f_file_to_attach_with_path, f_aws_region=None, f_aws_access_key_id=None, f_aws_secret_access_key=None)` sends via `boto3.client('ses').send_raw_email` instead — added because there's currently no working SMTP relay to test against. It resolves AWS credentials the same way `ClassS3FlagFile` does (env vars `AWS_KEY_1`/`AWS_KEY_VALUES_1`, i.e. the same S3 AWS key, sourced from `AWS_KEY/.env-EMSERVICEUSER`) unless explicit credentials are passed in, region defaults to `us-east-2`, and it raises `RuntimeError` (fail-closed) if no credentials are found. `ClassSASProgram.py` imports the class (`from Modules.m_mail_send_ONE_attach import ClassMailSend`) and picks between the two per-job at runtime — see `ClassSASProgram.f_send_email_or_post_to_webhook` below and the SES bullet under "Key conventions / gotchas" for why S3_Bucket_processing's FROM/TO/CC are overridden. The real module this import was originally written against lives at `/usr/local/vbin/common_py` on the actual SAS server (a flat file, no `Modules/` package there) — see "Local/dev environment substitutions" below.

The bucket/folder/file_mask *authorization* file itself (formerly `AWS_KEY/EMSERVICEUSER`) now lives per-job at `S3_Bucket_processing_<NAME>/info/s3_folder_mask_aws-key.info`, referenced by `z_config.f_get_prog_config('S3_Bucket_processing')['path_to_aws_key']`. Each line is an authorized `bucket|folder|file_mask|AWS_Key_Name|AWS_Key_Value` combination (see `ClassS3FlagFile` below), but the last two fields hold environment-variable **names**, not raw secret values (e.g. `$AWS_KEY_1`/`$AWS_KEY_VALUES_1` for line 1, `$AWS_KEY_2`/`$AWS_KEY_VALUES_2` for line 2, etc. — the number is the 1-based line number in the file). This is what makes `s3_folder_mask_aws-key.info` itself safe to commit to git.
- `TEST-CREATE-FLAG-FILE.sh` (repo root) — uploads an empty test `.FLAG` object straight to S3 (via this repo's own `.venv`/`boto3`, not the SAS-server one), matching the first `bucket|folder|file_mask` combination in `S3_Bucket_processing/info/s3_folder_mask_aws-key.info` and building a filename that satisfies that mask. Also drops a matching placeholder `.sas` file into `sas01_sasdata_PROD_S3_Bucket_processing/source/`, using the exact basename `ClassS3FlagFile` itself derives from the flag object name (split on `.PRD`, not on `.FLAG` — see `ClassS3FlagFile.py`), since the pipeline only processes a `.FLAG` file whose corresponding local `.sas` file already exists. Lets you exercise `ClassS3FlagFile`'s detection logic end-to-end without a real mainframe job dropping a flag file.
- `FAKE-SAS-BIN.sh` (repo root) — a bash emulator standing in for the real `sas` binary off the actual SAS server (see "Local/dev environment substitutions" below).
- `sas01_sasdata_PROD_S3_Bucket_processing` (repo root) — a gitignored, machine-specific symlink standing in for the real SAS server's `/sas01/sasdata/PROD/S3_Bucket_processing` directory (which has `log/` and `source/` subfolders). `z_config.f_get_prog_config('S3_Bucket_processing')['path_to_logfile']`/`['path_to_sasfile']` point at `../sas01_sasdata_PROD_S3_Bucket_processing/log` and `/source` (relative to the job folder cwd, same convention as other `z_config` path entries). `DEPLOYMENT.sh` checks this link exists and resolves to a real directory each run, prompting the deployer for the real path and creating it if not — see the `DEPLOYMENT.sh` description above.

## Core execution flow (S3 mode)

1. Cron invokes `S3_Bucket_processing-<NAME>.sh` with `cd` into the job's own folder first (relative paths like `../COMMON/...` assume this).
2. The script redirects stdout/stderr into `log-S3_Bucket_processing/<timestamp>--thread-N.log` (unless invoked with `test` as the first arg, which keeps output on the console) and calls `../COMMON/sas_ftp_and_S3_Bucket_processing.py`.
3. The entrypoint splits `-b <bucket>/<prefix>` into a bucket name and key prefix, loads `z_config_loggers-S3_Bucket_processing.ini`, and looks up `z_config.f_get_prog_config('S3_Bucket_processing')['path_to_aws_key']` for the credentials file path.
4. `ClassS3FlagFile` (`COMMON/Modules/ClassS3FlagFile.py`) opens that key file and scans its lines for one whose `bucket|folder|file_mask` fields exactly match the job's `-b`/`-m` values; if none match, it logs a critical error (naming bucket/folder/mask, never the key values) and `exit()`s — this is what allows one shared `COMMON/` codebase to serve multiple wrapper scripts, each restricted to its own authorized bucket/folder/mask combination. The matched line's key/secret fields are `$VAR`-style environment variable references, which it resolves via `os.environ` (fail-closed `exit()` if the variable isn't set) — those variables must already be exported into the process, which is why the `.sh` wrapper sources `../AWS_KEY/.env-<NAME>` before running Python. It then builds a `boto3.Session` from the resolved key/secret, confirms the bucket is reachable (`s3_bucket_exists`), lists objects under the prefix, and filters by the `-m` file mask — split on `*` into a `startswith`/`endswith` pair (e.g. `EMSERVICEUSER*.FLAG` → starts with `EMSERVICEUSER`, ends with `.FLAG`).
5. It picks the oldest matching object whose corresponding local `.sas` file (looked up via `z_config.f_get_prog_config('S3_Bucket_processing')['path_to_sasfile']`) and log dir (`['path_to_logfile']`) both exist, then copies the flag object to a `..._PROCESSED/<thread>/` key and deletes the original (`s3_move_flag_file`).
6. `ClassSASProgram` runs the actual SAS program (`sas -work ... -log ... -print ... -sysin <file> -nodms`), append-logs start/end to `log-S3_Bucket_processing/history.log`, scans the SAS log for `"ERROR: "` lines, and e-mails the result with the log attached — subject is `SAS-ERROR`, `SAS-SUCCESS`, or `SAS-WARNING` (no log file produced at all). `f_send_email_or_post_to_webhook` picks the delivery method from `self.mail_config['SMTP']` (set in `__init__` from `z_config.f_get_prog_config(self.system_short_name)['mail']`): the literal value `'SES'` calls `ClassMailSend.mail_send_ONE_attach_SES`, anything else is treated as a real SMTP server address and calls `ClassMailSend.mail_send_ONE_attach`. Either way FROM/TO come from `self.mail_config['from']`/`['to']` (CC forced to `[]`) — the real recipients in `info/<ENV>/S3_Bucket_processing.USERS`/`.FROM` are still read and logged but **not** used as the actual FROM/TO for sending — see the SES bullet under "Key conventions / gotchas".
7. `f_run_different_logic_after_run_any_sas` then gzips/backs up the `.PRD` file via `f_backup_one_prd_file` (only on `SUCCESS`, gated by `z_config.f_get_prog_config('S3_Bucket_processing')['compress']`). On `ERROR`, `.PRD` files are deliberately left in place so the `.FLAG` file can be safely resubmitted without re-sending data. (The mainframe-FTP branch in this function only fires for the `scoring/code_2` job from the parent repo — dead code in this S3-only tree.)

## Local/dev environment substitutions

This tree is being re-implemented to run independently of the real production environment (`sas-server.example.com`, the real `sas` binary, `/usr/local/vbin/common_py`, etc.). The one exception, permanently, is the real SAS executable itself — a SAS license is too expensive to have in a dev environment, so it stays emulated. Everything else (S3, SMTP, AWS credentials) stays **real infrastructure, just pointed at dev-safe targets** (e.g. the `EMSERVICEUSER-DEV` S3 folder, real internal SMTP relay) rather than emulated — see the `AWS_KEY/` and S3 bullets above.

- **Permanent, auto-managed by `DEPLOYMENT.sh`**: `COMMON/z_config.py`'s `sas_bin` points at `../FAKE-SAS-BIN.sh` unless `DEPLOYMENT.sh` detected a real `sas` executable on the machine (see the `DEPLOYMENT.sh` description above), in which case it rewrites this line to that real path — don't hand-edit `sas_bin`, re-run `DEPLOYMENT.sh` instead. `FAKE-SAS-BIN.sh` is not a SAS interpreter — it only emulates the real binary's `-log`/`-print`-directory-defaulting behavior (writes `<sysin-stem>.log`/`.lst` into the given dir) well enough for `ClassSASProgram` to find a log file afterward and scan it for `"ERROR: "`. Put the literal string `FORCE_SAS_ERROR` anywhere in a `.sas` file to make the fake binary emit an `ERROR:` line on demand (exercises the `SAS-ERROR` e-mail path); a missing/unreadable `-sysin` file makes it write no log at all (exercises `SAS-WARNING`).
- **Permanent, auto-managed by `DEPLOYMENT.sh`**: the repo-root `sas01_sasdata_PROD_S3_Bucket_processing` symlink (see the repository-layout bullet above) is machine-specific and gitignored, so it doesn't survive a fresh clone/new machine. `DEPLOYMENT.sh` re-verifies/recreates it each run — don't hand-create it once and forget it, and don't assume it exists just because `z_config.py` references it.
- **Environment-specific, not a hack to revert**: `S3_Bucket_processing/S3_Bucket_processing-EMSERVICEUSER.sh`'s real `${python_bin} ${prog_name_with_path} ...` call (the line that actually runs the pipeline) is commented out, because `python_bin` (`/usr/local/vbin/.venv/python3.9/bin/python`) is a path that only exists on the real SAS server, not in this independent dev environment. To run the entrypoint logic here, invoke it directly with this repo's own `.venv` python instead (e.g. from inside `S3_Bucket_processing/`: `set -a; source ../AWS_KEY/.env-EMSERVICEUSER; set +a; ../.venv/bin/python ../COMMON/sas_ftp_and_S3_Bucket_processing.py -t S3 -s S3_Bucket_processing -b your-s3-bucket/EMSERVICEUSER-DEV -d S3_Bucket_processing -n 1 -m '*.FLAG'`).
- **Environment-specific, not a hack to revert**: `COMMON/Modules/ClassSASProgram.py`'s import of `m_mail_send_ONE_attach` was changed from the original unqualified `from m_mail_send_ONE_attach import mail_send_ONE_attach` (which resolved against `/usr/local/vbin/common_py`, outside this git tree) to `from Modules.m_mail_send_ONE_attach import ClassMailSend`, matching this repo's copy living in `Modules/` as part of making the tree self-contained.
- **Environment-specific, not a hack to revert**: there's currently no working SMTP relay in this dev environment, so `S3_Bucket_processing`'s `l_prog_config` entry sets `mail.SMTP = 'SES'`, which makes `ClassSASProgram.f_send_email_or_post_to_webhook` call `ClassMailSend.mail_send_ONE_attach_SES` (AWS SES via boto3) instead of `mail_send_ONE_attach` (SMTP) — see the SES bullet under "Key conventions / gotchas" for the FROM/TO override this requires. `mail_send_ONE_attach` itself is untouched and becomes the active path again simply by changing that job's `mail.SMTP` back to a real server address once one is reachable.

## Key conventions / gotchas

- Naming is in English. Conventions: `_with_`/`_without_` in names mean "with"/"without" (e.g. `folder_with_flag_file`, `..._with_path`, `file_without_path`), and `l_`/`f_`/`c_` prefixes mark lists, function arguments and constants. The `.FROM` file holds the sender address and `.USERS` the recipients.
- `COMMON/z_config.py`'s `l_prog_config` entry for this job is keyed by the literal string `'S3_Bucket_processing'`. If you add a new S3 job/thread, add one new `l_prog_config` entry for it (see the `z_config.py` bullet above).
- Relative paths (`../COMMON/...`, `./info/...`) assume the script is invoked from inside its own job folder — `cd` there first, matching `_HOW_TO_RUN.txt` and crontab entries.
- Only the Linux users listed in `z_config.m_allowed_users` (`MRSERVICEUSER`, `EMSERVICEUSER`) may run `ClassSASProgram`; it calls `exit()` otherwise. This (and any other `exit()`/exception raised after the `___<systemname>___i_am_working__.thread_N` lock file is created) is why `sas_ftp_and_S3_Bucket_processing.py`'s `main()` wraps everything from flag-file creation through the SAS run in `try/finally` — the `finally` always removes that lock file, otherwise a run that exits early (e.g. run as the wrong OS user) leaves it behind and every subsequent run refuses to start, thinking a thread is already working. If you ever see "I-AM-WORKING-FILE (...) EXISTS. IT MEANS ONE TREAD IS ALREADY RUNNING." on a run where nothing is actually running, delete the stale `./___S3_Bucket_processing___i_am_working__.thread_<N>` file by hand.
- **`S3_Bucket_processing_MRSERVICEUSER` is stale/broken**: its wrapper script (`S3_Bucket_processing-MRSERVICEUSER.sh`) references `../COMMON/sas_ftp_processing_S3_Bucket_processing.py`, which does not exist (the real entrypoint is `sas_ftp_and_S3_Bucket_processing.py`), and it never sets/passes the now-required `-m` file mask argument. Its logs show no activity since December 2021 — it predates a rename/refactor of the entrypoint and argument interface. Don't treat it as a working reference for how the pipeline runs; use `S3_Bucket_processing` for that.
- Credentials (Snowflake passwords in `autoexec.sas`, AWS keys in `AWS_KEY/.env-*`) are plaintext by design of the existing system — never print/echo their contents, and avoid widening their exposure when editing nearby files. Both `autoexec.sas` and `AWS_KEY/.env-*` are gitignored; `S3_Bucket_processing/info/s3_folder_mask_aws-key.info` itself holds only env-var names, not secrets, so it's safe to commit.
- `S3_Bucket_processing/info/s3_folder_mask_aws-key.info` is an authorization allow-list, not just a credential store: `COMMON/` is designed to be reused by multiple wrapper scripts, each hardcoding its own S3 bucket/folder/file-mask combination. `ClassS3FlagFile` requires that combination to appear as a line in the key file — an unlisted combination is a hard failure (`exit()`), not a silent skip. When adding a new wrapper script/job, add its bucket/folder/mask/key line to the relevant key file first. `s3_folder_mask_aws-key.info` and `S3_Bucket_processing-EMSERVICEUSER.sh`'s `s3_bucket_with_dir` must always be kept in sync (same bucket/folder) or the job will hard-fail with no match.
- The real S3 target is `your-s3-bucket` in `us-east-2` (per `__NOTES_about_S3.txt`), with a separate folder per Linux user/environment (`EMSERVICEUSER-PROD`, `EMSERVICEUSER-DEV`, etc.). **Currently `s3_folder_mask_aws-key.info` and the EMSERVICEUSER wrapper point at `EMSERVICEUSER-DEV`** (still in development) — don't assume this is the production folder; switching to `EMSERVICEUSER-PROD` is a deliberate future step, not the current state.
- **SES is in sandbox mode under the `s3_user` AWS key** (the same key used for S3, resolved via `AWS_KEY_1`/`AWS_KEY_VALUES_1`) — every FROM/TO/CC address must be individually SES-verified or `send_raw_email` fails with `AccessDenied`. The real `.FROM` FROM address (`sas-status@notification.example.com`) and `.USERS` TO addresses (e.g. `user@example.com`, `user@example.com`) are **not** verified, so `S3_Bucket_processing`'s `l_prog_config` entry in `z_config.py` sets `mail.from`/`mail.to` to the one verified address (`user@example.com`) instead, and `ClassSASProgram.f_send_email_or_post_to_webhook` sends with those (`self.mail_config['from']`/`['to']`), CC forced to `[]`. This is a workaround for sandbox mode, not a permanent config — once the AWS account is out of SES sandbox (or the real addresses are verified), switch that entry's `mail.from`/`mail.to` back to the real `.FROM`/`.USERS`-derived addresses.
- `COMMON/Modules/f_ftp_scoring_status_file_to_mainframe.py` is still imported by the live entrypoint chain (`sas_ftp_and_S3_Bucket_processing.py` and `f_run_different_logic_after_run_any_sas.py`) but is functionally dead in this S3-only tree — the mainframe-FTP branch it feeds only fires for the `scoring/code_2` job from the parent repo, which doesn't exist here. Don't treat it as a living reference implementation.
- `__pycache__/`/`*.pyc` are gitignored; a batch of `.pyc` files committed before this rule existed were removed from tracking (`git rm --cached`) but are left on disk - don't re-add compiled bytecode.
